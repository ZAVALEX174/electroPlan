# ElectroPlan Pro — правила для Codex

Рабочий каталог и git-репозиторий — эта папка `electroplan-project/`. Отвечай владельцу по-русски.
Целевой продукт — 1С-Битрикс, но сейчас работает прототип на HTML/CSS/JS без сервера Битрикс.
Не применяй PHP- и Bitrix-процедуры к задачам прототипа. Исходные прайсы в родительской папке
не редактируй вручную.

## Перед работой

- Прочитай начало `HANDOFF.md` и последние записи по теме; подробные правила проверки и
  организации работы — `.claude/RULES.md`, разделы 7.1–7.3 (механику Claude адаптируй под
  Codex). Актуальные незакрытые задачи сверяй с `docs/ОСТАТОК-РАБОТ.md`. `PLAN.md` описывает
  и будущую платформу, а не только доступную сейчас инфраструктуру.
- Для вопроса из слов заказчика найди все относящиеся к теме места в `docs/расшифровка-*`,
  `docs/итоги-встречи-*`, `docs/письмо-*`, `docs/вопросы-*` по артикулам и синонимам. Сверь
  их с формулировкой владельца. Расхождение покажи до изменения кода.
- Сформулируй одним предложением наблюдаемый результат там, где человек его увидит:
  холст, окно поста, документ или сайт. Границу задачи задают слова владельца. Уже данное
  разрешение на работу не запрашивай повторно; уточняй только решение, без которого нельзя
  определить поведение продукта.

## Код и проверка

- Новую логику помещай в отдельный `js/<имя>.js`; в `js/app.js` оставляй только связку. Правило,
  влияющее на расчёт или подбор, держи в одной чистой функции и проводи ко всем потребителям.
- Проверяй края: соседние экраны и документы, старые сохранённые проекты, каталог без товара,
  денежные итоги, потерю данных и безопасность. Зелёный тест не доказывает правило, если только
  повторяет реализацию. Для денежных изменений проверь, что целевая мутация ломает тест.
- После реализации сделай независимую и состязательную проверку: конкретный вход, ожидаемый и
  фактический результат. На блок — до двух проходов проверки. Находки вне границы задачи и
  косметические улучшения занеси в бэклог; исправляй в текущем блоке неверную цену, состав,
  потерю данных или уязвимость.
- Перед завершением прогони подходящие тесты, `npm test` для значимого изменения, `git diff --check`
  и просмотри дифф. В `HANDOFF.md` явно запиши закрытый блок и оставшиеся ограничения.

## Субагенты Codex

- В сложной задаче поручай независимые части субагентам Codex: разведку, ограниченную реализацию,
  независимую проверку и поиск краёв. Корневой агент лично сверяет исходные факты, дифф и тесты,
  принимает продуктовые решения и коммитит. Субагенты не коммитят и не пушат.
- В задаче субагенту укажи подтверждённые факты и слова заказчика, ожидаемый результат, границы
  файлов, что нельзя сломать и требуемые доказательства. Не поручай неутверждённые изменения
  интерфейса или цены. Обычно не веди больше двух параллельных линий, если они трогают `app.js`
  или `index.html`. Для браузерных проверок разведи origin, чтобы агенты не делили localStorage.
- Не переноси имена агентов, модели, лимиты и команды Claude Code буквально: используй доступные
  роли и инструменты Codex, наследуя текущую модель по умолчанию. Общайся с владельцем во время
  долгой работы, а результат агентов проверяй по коду и наблюдаемому поведению.

## Публикация и предметные правила

- `main` сразу виден заказчику через GitHub Pages. Незавершённое держи в отдельной ветке;
  перед отправкой в `main` проверь влияние на действующий сайт и сохранённые проекты. Ветка
  `client` не является текущим превью заказчика. Не утверждай, что заказчик может загрузить
  файл в репозиторий: согласно `HANDOFF.md`, у него сейчас нет прав записи.
- Проходная определяется номером, который человек указал у клавиши; без номера — обычный
  выключатель. Механизм клавиши считает программа, ручной выбор человека главнее расчёта.
  Не перекладывай на человека работу, которую должна делать программа.
- Правила для Claude Code и её хуки находятся в `.claude/`; они не являются настройкой Codex.
  При работе с Битриксом отдельно проверь, что реальная среда и её параметры появились.
