# К9: один шаблон и загрузка прайса заказчиком

Постановка владельца 15.11.2026: передать заказчику один Excel-шаблон с фиксированными полями.
Заказчик заполняет его, загружает на сервер; программа получает опубликованный прайс, разбирает
строки и подставляет значения в нужные поля каталога. Это общий каталог для всех пользователей.
GitHub Pages сейчас показывает общий статический каталог из `main`. Это временный способ
раздавать одну версию всем пользователям; сам сайт не принимает запись Excel-файла.

## Что уже сделано

- К9(1): кнопка «Прайс по шаблону» скачивает Excel-шаблон, проверяет заполненный файл и показывает
  ошибки/предупреждения. Правила столбцов — `js/priceTemplate.js`, разбор листа — `js/priceSheet.js`.
- Шаблон содержит 28 смысловых полей из двух файлов `Номенклатура новая.xls` и
  `Номенклатура 2026-10-10.xls`. Одинаковые поля с разными названиями сведены в один столбец:
  «Серия» → «Коллекция», «Размер в модулях» → «Количество модулей», «цена, евро» →
  «Прайс розница РФ, Евро», «Цвет элемента» → «Цвет механизма». Добавлены бренд, код цвета
  накладки, описание особенностей, подпись для картинки и «Изображение» (ссылка на фото).
  Пустая ссылка сохраняет прежнее фото артикула; новая заменяет его при публикации каталога.
- `js/priceCatalog.js` преобразует проверенные строки этого шаблона в товары каталога без записи
  в хранилище. Проверка файла показывает число и первые позиции, которые удалось расшифровать.
  Преобразователь принимает `existingProducts`, чтобы сохранять ID и изображения по артикулу.
- Текущая новая номенклатура уже преобразована в статический каталог и доступна заказчику на
  GitHub Pages. Проверка файла пока не изменяет этот каталог.
- `DataService.getProducts()` имеет асинхронный режим `api`, но серверный каталог ещё не подключён.
- Временный режим `static` читает `catalog/current.json` и указанную там неизменяемую версию.
  Проверяются формат, состав и SHA-256. При сбое используется встроенный каталог; сайт открывается.
- Проект с товарами сохраняет свою версию каталога в `catalogSnapshot` (компактный формат
  `js/projectCatalog.js`, включая автоматически подбираемые товары). При открытии браузерного
  сохранения или файла проекта расчёт и документы используют эту версию, включая цены и размеры
  упаковок. Новые проекты получают актуальный общий каталог. Старые проекты без снимка закрепят
  текущую версию при следующем сохранении; их прежний каталог восстановить задним числом нельзя.

## До появления Битрикс

GitHub остаётся временным местом публикации общего прайса. У заказчика сейчас нет прав записи
в репозиторий: он передаёт заполненный шаблон владельцу проекта. Владелец выпускает его
локальной командой. Команда не делает git commit/push и не хранит ключи на публичной странице.
Первая статическая версия содержит ровно те же 3364 товара, что действующий встроенный каталог:
само подключение загрузки не меняет цены и состав. Самостоятельная загрузка заказчиком потребует
защищённого механизма или выдачи ему прав на репозиторий.

### Выпуск владельцем

1. Проверить файл в окне «Прайс по шаблону». Повторно прогнать проверку и получить отчёт изменений
   без записи: `node tools/publish-price.mjs --file "ПУТЬ-К-ФАЙЛУ.xlsx"`.
2. Сверить список добавленных, обновлённых, отсутствующих артикулов и каждое изменение цены.
   Отсутствующие в файле товары по умолчанию сохраняются в каталоге. Если их действительно надо
   снять, повторить с `--retire-missing`; тогда они останутся с прежними данными и `active:false`.
3. Только после проверки выполнить ту же команду с `--publish`. Она создаёт неизменяемый
   `catalog/versions/<SHA-256>.json`, отчёт `catalog/reports/<SHA-256>.json` и переключает
   `catalog/current.json`. Ошибка до переключения оставляет прежнюю версию активной.
4. Проверить дифф, тесты и открытие сохранённых проектов; затем владелец коммитит и отправляет
   файлы в `main`, откуда GitHub Pages раздаёт новую версию всем пользователям.

Для отката: `node tools/publish-price.mjs --rollback <SHA-256> --publish`, затем проверить
`catalog/current.json` и отправить изменение в `main`. Старый файл версии и его исходный отчёт
остаются на месте. Исходные файлы прайса команда не редактирует.

## Что остаётся для полного сценария

1. Перед первым обновлением **цен** общего каталога проверить несколько сохранённых проектов
   заказчика: открытие, смету и КП. Файлов проектов заказчика в рабочей папке нет. Проверка с
   полным каталогом (включая геометрию фото), предельным планом и запасом данных даёт около
   4,70 млн символов против проверенной квоты около 5,2 млн; запас невелик.
2. Когда появится сервер и авторизация, перенести туда приём файла и хранение версий. Пока
   заказчик сам не загружает файл на GitHub Pages.

Пока ветка К9 не включена в `main`, сайт заказчика и его текущий каталог не меняются.
