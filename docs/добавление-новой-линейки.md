# Как добавить новую линейку и не потерять качество сборки

Порядок действий, когда заказчик присылает новую номенклатуру/прайс (например линию
с артикулами 30 и 31). Всё воспроизводимо: те же входные файлы дают тот же результат.

## Коротко — четыре команды

```bash
npm run build:catalog    # состав и цены  → js/catalog-vimar.js
npm run build:attrs      # признаки поста → js/catalog-vimar-attrs.js
npm run build:openings   # окна накладок  → js/catalog-vimar-openings.js
npm run build:faces      # лица механизмов → js/catalog-vimar-faces.js
npm test                 # 228 тестов
```

Затем глазами — стенд `preview-posts.html` (открыть через локальный сервер) и конструктор.

Первые две команды читают файлы заказчика, вторые две — фотографии с vimar.ru
(кэш в `.tmp-openings/` и `.tmp-faces/`, повторный прогон сети не касается).

## От чего зависит «качество» сборки

Изображение собранного поста складывается из четырёх слоёв, и каждый может отвалиться
по своей причине. Ничего при этом не ломается — картинка просто становится беднее.

| Слой | Откуда берётся | Если данных нет |
|---|---|---|
| Фото накладки | индекс картинок → `imageUrl` товара | рисуется пластина цветом из названия |
| Окна накладки | `build:openings` по фото | окна делятся пропорцией (`splitOpening`) |
| Разбиение на посты | колонка «Размер в модулях» → `layoutRows` | немецкая накладка станет сплошной, как итальянская |
| Фото механизма | индекс картинок + `build:faces` | рисуется клавиша в цвет механизма |

## Слабое звено — картинки

Ссылки на фотографии приходят НЕ из номенклатуры и НЕ из прайса, а из заранее собранных
индексов (скрейпинг сайтов VIMAR):

- `../outputs/db_price_import_20260723/vimar-ru-image-index.json` — 3869 позиций vimar.ru
  (приоритетный);
- `../outputs/db_price_import_20260723/vimar-image-index.json` — 558 позиций vimar.com.

Формат — плоский массив `{ code, preview_image_url, image_url, product_page_url, image_source }`,
сопоставление с товаром по артикулу без учёта регистра.

**Новых артикулов в этих индексах не будет.** Значит для новой линейки индекс надо
пополнить, иначе вся линия поедет на нарисованные клавиши. Варианты:

1. попросить у заказчика выгрузку изображений (он подтвердил: «можно их спросить и
   сохранить», и они уже есть на старом сайте);
2. заново снять индекс с vimar.ru по новым артикулам и дописать в тот же JSON —
   формат простой, дописывание безопасно, дубликаты перекрываются последним значением.

Путь к индексу можно указать флагом:

```bash
npm run build:catalog -- --images "../outputs/новый-индекс.json"
```

## Что проверить после прогона

**1. Отчёт `build:openings`.** Он сам называет накладки, у которых число найденных окон
не совпало с ожидаемым по названию. Это признак либо нестандартного кадра, либо
неверной раскладки. Точечная перепроверка:

```bash
npm run build:openings -- --bases 09673,09664,09666
```

**2. Отчёт `build:faces`.** Отдельно перечисляет:
- «составные» позиции — в кадре несколько предметов (пара клавиш), фото не используется,
  позиция уходит на клавишу-фолбэк. Это нормально;
- «подозрительные» — единственный предмет, но пропорция не сошлась с ожидаемой по числу
  модулей. Такие надо глянуть глазами: чаще всего рядом с модулем лежит комплектный
  аксессуар (косичка HDMI, коннектор RJ45) — детектор их отсекает, но кадр стоит
  проверить.

Точечно:

```bash
npm run build:faces -- --codes 09001,09005.2.CM,14346
```

**3. Немецкие накладки.** У них в `layoutRows` должна быть раскладка вида `[[2,2]]`,
`[[2,2,2]]`. Если у новой линейки колонка «Размер в модулях» заполнена иначе — накладка
поедет как итальянская, одним сплошным окном. Проверять по накладкам «2+2» из новой линии.

**4. Стенд `preview-posts.html`.** Добавьте туда пару позиций новой линейки (массив
`cases` в конце файла: заголовок, артикул накладки, артикулы механизмов) и посмотрите
все три размера сразу — конструктор, документ, миниатюра.

## Если у новой линейки другой стиль фотографий

Вся геометрия держится на двух допущениях, проверенных на текущем каталоге VIMAR:
монтажное окно накладки залито на фото чистым белым, а механизмы сняты фронтально и
лицо модуля имеет отношение ширина/высота = `число модулей × 22,5/45`. Если новая линия
снята иначе (в перспективе, на цветном фоне, с тенями), крутятся именованные константы:

| Константа | Файл | Что делает |
|---|---|---|
| `TRIM` | `tools/lib/faces.mjs` | поджатие лица внутрь, срезает кромку рамки механизма (2 %) |
| `ASPECT_TOL` | `tools/lib/faces.mjs` | допуск на пропорцию при выборе предмета в кадре (±15 %) |
| `VOPEN_FRACTION` | `tools/lib/faces.mjs` | радиус размыкания, рвущий провод между модулем и аксессуаром |
| `MODULE_RATIO` | `tools/lib/faces.mjs` | геометрия модуля 22,5/45 — менять только для другого бренда |
| `IMPOST_GAP` | `js/postImage.js` | зазор под импост в запасном расчёте окон |
| `KEY_SEAM`, `KEY_RADIUS`, `KEY_LUMA_SHIFT` | `js/postImage.js` | вид нарисованной клавиши-фолбэка |

Константы из `tools/` запечены в сгенерированные файлы — после их правки нужен повторный
`npm run build:faces` / `build:openings`.

## Другой бренд (не VIMAR)

`MODULE_RATIO = 22,5/45` — это модульный стандарт VIMAR. У другого бренда своя сетка,
и детектор лиц придётся параметризовать по бренду. Всё остальное (окна по фото, раскладка
по постам, фолбэки) от бренда не зависит.
