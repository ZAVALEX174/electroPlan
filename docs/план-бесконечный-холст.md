# План: бесконечный холст с панорамированием и зумом

> Утверждено владельцем проекта 2026-07-30. Реализуется отдельным блоком после
> завершения правок по сетке и привязкам.

## Зачем

Сейчас холст — блок фиксированного размера с CSS-масштабом (`transform: scale()`,
`transform-origin: top left`). Следствия, которые упёрлись в реальную работу:

- при уменьшении масштаба холст съёживается, вокруг остаётся пустое серое поле;
- за границы блока ничего не выходит: координаты объектов зажимаются
  (`Math.max(0, Math.min(canvas.clientWidth - el.offsetWidth, …))` в `makeDraggable`);
- перемещаться по плану нельзя — панорамирования нет вовсе;
- зум идёт от левого верхнего угла, а не от курсора, поэтому «прицелиться» невозможно.

## Что делаем (утверждённый объём)

| Возможность | Решение |
|---|---|
| Панорамирование | зажатый **пробел** + перетаскивание, **средняя кнопка мыши** |
| Зум | **колесо мыши к позиции курсора** + существующие кнопки +/− |
| Границы | формально бесконечные, объекты **не обрезаются** |
| Возврат | кнопка **«Вписать в экран»** |

## Ключевая идея реализации

Развязать **мировые координаты** (в которых живут объекты, линии, помещения) и
**экранное представление**. Вводится вид (viewport): смещение `panX/panY` + масштаб.
Экран ↔ мир пересчитываются двумя функциями, и только они знают про DOM.

Это ломает текущее допущение «координата на холсте = координата в элементе»,
поэтому затрагивает почти всё, что рисует.

## Что затрагивается — проверить каждое

1. **Слои SVG** (`#wallsSvg`, `#roomsSvg`, `#markupSvg`, `#detectSvg`, `#scaleSvg`) —
   сейчас растянуты по размеру блока. Нужен общий `viewBox`, иначе слои разъедутся
   между собой при панорамировании.
2. **Подложка-чертёж** (`#planImage`) — сейчас `object-fit: contain` по размеру блока.
   Должна жить в мировых координатах вместе со всем остальным.
3. **Пиктограммы объектов и подписи комнат** — это HTML-элементы с `left/top` в пикселях;
   их позиционирование должно идти через пересчёт мир→экран.
4. **Перетаскивание** (`makeDraggable`) — снять зажим по краям блока, делить на масштаб вида.
5. **Клики по холсту** — `canvas.onclick`, `addWallPoint`, `addRoomLinePoint`, `addScalePoint`:
   везде экран→мир.
6. **Расчёт связных областей** (`EPGeom.buildSpaceComponents`) — сейчас берёт
   `canvas.clientWidth/clientHeight`. На бесконечном поле нужны **границы по факту
   нарисованного** (bounding box линий и стен + запас), иначе сетка либо не покроет
   объекты, либо станет гигантской.
7. **Автообрисовка** (`autoTracePlan`) — привязка результата к отображаемому плану
   считает смещение и масштаб от размера блока.
8. **Масштабная линейка** и **правка вершин** (`dragVertex`) — те же пересчёты.

## Требования

- **Ничего не должно «поехать»**: линии, помещения, объекты и подложка обязаны
  оставаться на своих местах друг относительно друга при любом зуме и панорамировании.
  Это главный критерий приёмки.
- Обратная совместимость: сохранённые проекты открываются, координаты не пересчитываются
  задним числом (мировые координаты = текущие координаты холста).
- Вид (смещение и масштаб) сохраняется в проекте — чтобы вернуться туда, где работал.
- «Вписать в экран» подгоняет вид так, чтобы всё нарисованное поместилось с полями.
- Производительность: панорамирование и зум не должны перерисовывать всё подряд на
  каждое движение мыши.
- Конвенции прежние: без сборщика, namespace, чистые пересчёты — в тестируемый модуль.

## Риск

Самая опасная часть — пункт 6 (границы для расчёта областей) и пункт 7 (автообрисовка):
там координаты завязаны на размер элемента неявно. Если ошибиться, привязка оборудования
к помещениям и результат автообрисовки разъедутся с картинкой, причём не сразу заметно.
Поэтому приёмка — обязательно с проверкой в браузере на реальном чертеже.
