## 1. Техника рисования линий поверх изображения

**У донора.** Стек — Fabric.js (canvas). Подложка-«калька» — обычный
`fabric.Image`, уведённый на задний план (`sendToBack`/`sendObjectToBack`), поверх
рисуются линии как `fabric.Line`
(`backgroundImage.js:48-57`, `:145-196`). Картинка при загрузке ресемплится до
2200 px по большей стороне и вписывается в ~80 % видимой области
(`backgroundImage.js:30`, `:92-112`, `:154-163`).

Система координат: единая «сцена» Fabric, а зум/панорамирование — через
`viewportTransform` (матрица) на всём холсте
(`canvasViewport.js:50-57`, `:114-154`; зум 0.1–5.0). Линия хранится в **локальных**
координатах объекта (`x1,y1,x2,y2` + `left,top`), поэтому для любой работы с
геометрией её сначала переводят в абсолютные координаты сцены
(`geometry.js:50-68` — `getLineAbsoluteEndpoints`). Это источник постоянной возни:
почти каждая функция начинается с пересчёта endpoint'ов.

**У нас (важное отличие в нашу пользу).** Мы на SVG + CSS-масштабе. `#planImage` и
слои `#roomsSvg/#wallsSvg/#scaleSvg` лежат в одном контейнере `#canvas`
(`index.html:108-113`) и масштабируются вместе (`state.scale`, координаты клика
делятся на `state.scale` — `app.js:857-859`). Значит **линии автоматически лежат
поверх подложки в одной системе координат при любом зуме** — нам не нужны ни
`viewportTransform`, ни перевод локальных координат в абсолютные. Вся сложность
донора из п.1 у нас уже решена архитектурой SVG.

Берём: приём «подложка сзади, рисуем поверх» (у нас уже так).
Отбрасываем: весь слой `getLineAbsoluteEndpoints`/`viewportTransform` — нам не нужен.

## 2. Модель данных линии

**У донора.** Линия — `fabric.Line` c `id` (`line_<ts>_<rnd>`,
`lineModel.js:240-242`) и объектом `properties`, где среди прочего лежат
`startNode`/`endNode`, `layerId`, `length` и предметные поля вентиляции
(`lineModel.js:130-165`). Есть нормализация/миграция старых полей при загрузке
(`lineModel.js:187-216`). Узлов как отдельных сущностей в модели нет — узел
существует «виртуально»: это уникальная точка, в которой сходятся концы линий.
Он материализуется на лету в графе по ключу координаты
(`networkBuilder.js:73-126`, ключ через `getPointKey`, округление до 0.01 px).

**Редактирование.**
- Перетаскивание всей линии или одного конца: `object:moving` → `canvasLineDrag.js`.
  Конец «свободен» (можно тащить) только если в его узле сходится ≤1 линия;
  иначе конец «залочен», чтобы не рвать сеть (`canvasLineDrag.js:46-159`).
- Перетаскивание узла-пересечения тащит за собой все смежные линии: у каждой
  входящей меняется конец, у исходящей — начало (`canvasNodeDrag.js:37-121`).
- Разрезание линии в точке (клик по существующей линии при рисовании) —
  `splitLineAtPoint` делит на два сегмента, пропорционально распределяя длину
  (`intersections.js:571-745`, вызовы — `canvasSetup.js:528`, `:638`).

**Удаление.** Через удаление fabric-объекта с холста; граф перестраивается сам
(`updateConnectionGraph`, debounce 100 мс — `networkBuilder.js:167-194`).

Берём: идея «линия = {id, a, b, meta}; узел не хранится, а выводится из совпадения
координат концов»; разрезание линии в точке пересечения как основа для чистого
планарного графа. Отбрасываем: предметные `properties` вентиляции целиком.

## 3. Привязки (магниты)

**У донора** (`canvasSnap.js`):
- **Сетка**: `snapToGrid` — округление к `GRID_SIZE` (`canvasSnap.js:34-36`).
- **К узлам сети**: `findNearestNetworkNode(pointer, 18)` — ближайший узел в
  радиусе **18 px**, приоритетнее сетки (`canvasSnap.js:77-94`; в рисовании
  перебивает grid-snap — `canvasSetup.js:507-516`).
- **К точке на линии**: `findLinesInArea` + условие `param ∈ (0.05; 0.95)` —
  привязка к телу линии, но не к её концам (там сработает узловая привязка); при
  этом линия разрезается в точке привязки (`canvasSnap.js:103-111`,
  `canvasSetup.js:518-547`).
- **Индикатор-кандидат**: полупрозрачное кольцо `fabric.Circle` —
  зелёное R14 для узла, жёлтое R9 для точки на линии
  (`canvasSnap.js:22-25`, `:47-75`, `:96-113`).
- **Пересечения**: считаются попарно `lineIntersection` (параметрический метод
  `ua,ub ∈ [0,1]` — `geometry.js:146-170`), затем сливаются близкие
  (`mergeNearbyIntersections`) и кластеризуются к сетке (`intersections.js:36-77`,
  `:337-387`). Отдельной «привязки курсора к пересечению» при рисовании нет —
  пересечения материализуются позже, кнопкой «Разделить».

**Замыкание контура.** У донора **нет** — им не нужны замкнутые контуры (сеть, а
не помещения). Это нам придётся добавить самим (подсветка первой точки + клик по
ней). Плана-образца тут нет.

Берём: двухуровневый магнит (узел R≈18 приоритетнее сетки; к телу линии по
`param 0.05–0.95`); кольцо-индикатор кандидата; параметрический
`lineIntersection`. Отбрасываем: кластеризацию пересечений к сетке (у нас магнит
и так по сетке), cross-layer-логику.

## 4. Скрытие подложки

**У донора — два независимых механизма:**

1. **Подложка-картинка** (`backgroundImage.js`): кнопка «Скрыть/Показать» —
   бинарно `visible=false/true` (`:216-223`), **плюс отдельный слайдер
   прозрачности** `opacity` 5–100 % (`:225-232`). То есть «полупрозрачный режим»
   у них получается не третьим состоянием, а слайдером поверх бинарного скрытия.
   Плюс кнопка «Заблокировать» — снимает `selectable/evented`, чтобы картинка не
   мешала рисовать поверх (`:202-214`). Подложка исключена из расчёта, сохранения
   проекта и экспорта PDF (комментарий `backgroundImage.js:8-11`).

2. **Скрытие объектов** (`objectVisibilityToggle.js`) — тут удачное решение,
   которое стоит перенять: объект не удаляется и не гасится `visible`, а получает
   `opacity:0` + `selectable/evented:false`, и на его месте рисуется **пунктирный
   контур-«призрак»** (`fabric.Circle`, dashed), чтобы было видно, что здесь
   что-то есть (`:162-203`, `:218-230`). Состояние — флаг `state.objectsHidden`.
   Перед сериализацией скрытые объекты временно восстанавливаются, чтобы скрытие
   не «запеклось» в сохранении (`prepareObjectVisibilityForSerialization`,
   `:348-374`; тот же приём в undo — `undoRedo.js:33-44`).

Берём: идею три-состояния (показать / полупрозрачно / скрыть) — это ровно наш
Этап 1 и решение владельца №2; приём «скрытие ≠ удаление, состояние отдельным
флагом, не запекать в сохранение». Отбрасываем: «блокировку» подложки (у нас
подложка — фоновая картинка `#planImage`, она и так не перехватывает клики холста)
и пунктирный «призрак» (для целого чертежа не нужен — у нас полупрозрачный режим
эту роль выполняет лучше).

## 5. Деление области линиями на замкнутые части — САМОЕ ВАЖНОЕ

**Ответ: у донора этого НЕТ.** Проверено по `networkBuilder.js`, `chainAnalysis.js`,
`intersections.js` — ни поиска граней, ни минимальных циклов, ни полигонов
помещений. Их граф — про потоки воздуха, а не про площади:

- `buildNetworkGraph` строит рёбра/узлы (`networkBuilder.js:73-161`);
- `buildLineChains` сворачивает граф в **одномерные «цепочки»** — пути между
  «специальными» узлами (степень ≠ 2, тупики, узлы с оборудованием;
  `networkBuilder.js:380-671`, спецузлы — `:447-461`). Это обход путей, а не
  обход граней; замкнутое кольцо без ответвлений они обрабатывают как особый
  случай одной цепочки (`:456-461`), а не как «помещение».

Что у донора **есть полезного для нашего Этапа 3** — подготовка чистого планарного
графа:
- попарный поиск всех пересечений `findAllIntersections` (O(n²),
  `intersections.js:36-77`);
- слияние близких пересечений `mergeNearbyIntersections`
  (`intersections.js:337-387`);
- разрезание каждой линии по её пересечениям на сегменты
  (`_collectSplitsForLayer` → `splitAllLines`, `intersections.js:394-569`);
- дедупликация узлов по округлённому ключу координаты
  (`getPointKey`, `networkBuilder.js:88-89`, `intersections.js:526-531`).

Это ровно предобработка, после которой можно искать грани. Но **сам поиск граней
(минимальные циклы обходом «самое правое ребро по углу») донор не делает — это
пишем мы**. Наш существующий `EPGeom.buildSpaceComponents` (флуд-фолл по сетке,
`js/geometry.js:48-85`) — это как раз запасной алгоритм из плана, и он у нас уже
лучше, чем что-либо у донора по этой части.

Берём: конвейер «найти пересечения → слить близкие → разрезать линии на сегменты →
дедуп узлов по ключу координаты» как вход для планарного графа. Отбрасываем:
`buildLineChains` целиком (одномерные пути нам не нужны).

## 6. Удачные решения UX, которых у нас нет

Из донора стоит перенять:
1. **Preview-линия при рисовании** — пунктир от стартовой точки к курсору,
   контрастная тень для читаемости на любом фоне (`canvasSetup.js:577-596`).
   У нас сейчас стена появляется только по второму клику, без «резинки».
2. **Индикатор-магнит** — кольцо в точке-кандидате привязки (см. п.3). Наглядно
   показывает, куда «прилипнет» точка.
3. **Разрезание существующей линии кликом** — клик по телу линии создаёт узел и
   продолжает разметку от него (`canvasSetup.js:518-547`, `:635-658`). Позволяет
   пристраивать перегородки к готовым стенам.
4. **Перетаскивание конца линии** с защитой узлов степени > 1 от разрыва
   (`canvasLineDrag.js:46-159`) — совпадает с открытым у нас PLAN 3.2.
5. **Undo целым снимком** (`undoRedo.js:26-52`) — у нас снимок проекта уже есть
   (`projectSnapshot`), логику отмены можно построить на нём же.
6. **Автопересчёт с debounce** (`updateConnectionGraph`, 100 мс) — образец для
   «пересчёта помещений с задержкой» (решение владельца №3).

## Конкретный план переноса на нашу архитектуру

Учтены решения владельца по спорным вопросам (разметка — отдельный слой; скрытие
чертежа — три состояния; пересчёт — кнопка + авто с задержкой; ручная разметка
приоритетнее автоматики; нумерация — как сейчас).

### Этап 1. Скрытие чертежа (три состояния)
Новых модулей не нужно — это DOM + state, место `app.js` (оркестратор).
- `index.html`: кнопка-переключатель в `.trace-panel` (рядом с
  `#clearAutoTraceBtn`, `index.html:51-70`), три подписи по циклу.
- `css/styles.css`: классы `#planImage.plan-translucent{opacity:.4}` и
  `.plan-hidden{opacity:0}` (или инлайн `style.opacity`). Скрывается **только**
  `#planImage`; слои `#roomsSvg/#wallsSvg` не трогаем.
- `js/app.js`: `state.planVisibility ∈ {'show','dim','hide'}`, функция
  `setPlanVisibility(mode)` (тонкая обёртка), горячая клавиша; добавить поле в
  `projectSnapshot()` (`app.js:896-907`) и восстановление при загрузке
  (`app.js:938`). Логику расчётов не трогаем.
- Сложность: **низкая (~0.5 дня)**. Изолированно, ломать нечему. **Делать первым.**

### Этап 2. Рисование линий разметки (отдельный слой + магниты)
- **Отдельный слой** (решение №1): `state.markupLines` — независим от
  `state.walls`/`state.autoWalls`. Новый `<svg id="markupSvg">` в `#canvas`
  (`index.html:108-113`) и его отрисовка отдельным стилем (визуально отличать от
  авто-стен — п. Этап 2 плана). Новый инструмент разметки в `.tool-grid`
  (`index.html:75-81`) либо переключатель «стена / разметка» у инструмента `wall`.
  Текущий `addWallPoint`/`drawWalls` (`app.js:857-894`) остаются как есть.
- **Магниты** — чистые функции, место — `js/geometry.js` (`EPGeom`, дополняем):
  - `nearestEndpoint(point, segments, radius)` — ближайший конец линии;
  - `nearestOnSegments(point, segments, radius)` — ближайшая точка на теле линии
    (переиспользуем `distancePointToSegment`, `js/geometry.js:36-41`; параметр
    исключения концов — как у донора `0.05–0.95`);
  - `snapCandidate(point, segments, opts)` — сводит приоритет «узел → тело линии →
    сетка», возвращает `{x,y,kind}` для индикатора.
  Радиус привязки — в конфиг (PLAN 2.3), не константой. В проекте пока нет
  `js/config.js`; предложение — завести маленький неймспейс `window.EPConfig`
  (или объект-константу в `app.js`) под snap-радиус и cell/wallRadius. **Это
  решение на согласование** (см. «Вопросы»).
- **UX из донора**: preview-«резинка» (SVG `line` со `stroke-dasharray`),
  кольцо-индикатор кандидата (SVG `circle`), Backspace — снять последнюю точку,
  Shift — свободный угол (сейчас в `addWallPoint` угол принудительно
  ортогонализируется, `app.js:862-863`), замыкание контура кликом по подсвеченной
  первой точке. Всё — тонкие обработчики в `app.js`, геометрия — в `EPGeom`.
- Сложность: **средняя (1.5–2 дня)**. Риск — аккуратность привязок и preview.

### Этап 3. Помещения из линий (ядро) — пишем сами
Новый **чистый модуль** `js/roomsFromLines.js` (namespace `EPRoomsFromLines`),
двойной экспорт, без state/DOM — по образцу `js/geometry.js`. Покрываем
автотестами (`npm test`, node:test).
- Проход 1 (точный) — **грани планарного графа**:
  1. `splitAtIntersections(segments)` — по мотивам донора
     (`intersections.js:394-463`): все пересечения через
     `EPGeom` (проекция/детерминант, аналог `geometry.js:146-170`), затем
     разрез линий на сегменты в точках пересечения.
  2. `buildPlanarGraph(segments)` — дедуп вершин по округлённому ключу координаты
     (идея `getPointKey`), список смежности с углами рёбер.
  3. `findFaces(graph)` — **новое, у донора нет**: минимальные циклы обходом
     «следующее ребро по наименьшему углу поворота», отбрасывание внешней грани
     по знаку площади (`EPGeom.polygonAreaPx`, `js/geometry.js:18-23`).
  4. каждая грань → полигон помещения (без «лесенок»).
- Проход 2 (запасной) — если контур не замкнут: существующий
  `EPGeom.buildSpaceComponents` (`js/geometry.js:48-85`) + трассировка границы
  компонента в полигон с упрощением/ортогонализацией.
- Обёртка в `app.js` (тонкая): `buildRoomsFromLines()` — читает
  `state.markupLines`, зовёт `EPRoomsFromLines`, формирует `state.rooms` с
  `autoPolygon:true`; **сохраняет вручную поправленные** (`autoPolygon===false`) —
  ровно как уже сделано для OpenCV/ML (`app.js:326-335`, `:354-362`); продолжает
  нумерацию (`app.js:330`); затем `recalculateRoomAssignments()`
  (`app.js:587-601`). Кнопка «Определить помещения по линиям» +
  автопересчёт с задержкой (решение №3) — по образцу `scheduleSave`
  (`app.js:922`) и debounce донора. Незамкнутый контур — честное сообщение через
  `toast`, а не молчаливый пропуск.
- Приоритет ручной разметки над автоматикой (решение №4): помещения из линий
  затирают только авто-контуры (`autoPolygon:true`), ручные переживают пересчёт —
  механизм уже есть в наших detectRooms*.

## Чего найти не удалось

- **Алгоритма деления площади на замкнутые помещения у донора нет** (проверено в
  трёх графовых модулях). Это не пропуск в изучении — этого у них действительно
  нет; ядро Этапа 3 придётся писать самостоятельно.
- **Замыкания контура и подсветки первой точки** у донора нет (им не нужны
  замкнутые контуры) — образца для этой части UX не существует.
- Файлы `chainAnalysis.js`, `layersManager.js`, `imageManager.js` пролистаны
  точечно грепом: `chainAnalysis` — про анализ воздушных цепочек (нерелевантно);
  `imageManager`/`layersManager` — управление объектами и слоями горизонтов
  (cross-layer), для разметки помещений не нужны. Глубоко не читались осознанно,
  чтобы не тянуть их предметную специфику.
