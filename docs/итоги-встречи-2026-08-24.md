## 2. Логика схем электрики — ТЗ (главное нововведение)

Источник: сообщение заказчика 25.08 + презентация (слайды 6–9) + записи встречи.

### 2.1 Модель

Клиент выбирает **схему электрики** проекта: `Классическая` / `Реле` / `Звонковые кнопки`.
Для «классической» и «реле» на **каждую клавишу** указывается **группа света**.
Конфигуратор считает, сколько раз повторяется каждая группа, и **сам подбирает механизм**.

**Пользователь выбирает КЛАВИШУ, а не механизм.** Механизм подставляется автоматически.
Клавиша надевается на механизм; бывает **широкая или узкая** (`ХХ021` / `ХХ022` / `ХХ023`
— 1/2/3-клавишные). Из записи: *«механизм как бы один, а клавиша либо широкая, либо узкая
надевается»*.

### 2.2 Классическая схема

Пусть группа света включается с **N мест**:

| N | Механизмы |
|---|---|
| 1 | Выключатель `ХХ001.0` |
| 2 | Два переключателя `ХХ005.0` (на каждом месте) |
| N ≥ 3 | Два переключателя `ХХ005.0` + **(N − 2)** инвертора `ХХ013.0` |

Терминология заказчика (подтверждена презентацией): **Выключатель / Переключатель /
Инвертор**. «Инвертор» = перекрёстный. Мастер-выключатель = дополнительный обычный
выключатель.

### 2.3 Схема с реле

- За каждой кнопкой — механизм `ХХ008.0`.
- На **каждую уникальную группу** — импульсное реле **03992**.
- Мастер-выключатель = дополнительная кнопка (в презентации — RESET push button).
- **Ограничение из презентации: до 4 кнопок на одно реле** (ON/OFF push button ×4).
  Это преимущество релейной схемы — до 4 мест управления без переключателей.

### 2.4 Звонковые кнопки

**⚠️ Не описаны нигде** — ни в презентации, ни в опроснике, ни внятно на записи
(упомянуты вскользь: «есть ещё звонковые кнопки для реле, там диммеры, всё остальное»).
**Требуется отдельный ответ заказчика.**

### 2.5 Что это требует от кода

Поля **«группа света» в модели объекта проекта нет вообще** (проверено по всему `js/`).
Это новая сущность: у клавиши/поста — номер группы; на уровне проекта — реестр групп;
подбор механизма — функция от числа вхождений группы и выбранной схемы.

Подтверждение из реального плана дизайнера (`Электрика этаж 1.pdf`): у каждого выключателя
проставлены номера групп (`71 72`, `81 82 83`, `4.1 4.2`), в легенде — нумерация
«Помещение (2) Группа освещения (1)» → `2.1`, и уже присутствуют «выключатель 1-клавишный
**проходной**» и «2-клавишный проходной» — то есть переключатели. Модель заказчика
полностью совпадает с тем, как это рисуют дизайнеры.

## 3. Найденные баги (подтверждены)

### 3.1 🔴 Суппорт не умножается на число постов — смета занижена

**Подтверждено заказчиком на записи** (20:29, ~24:23):
> «с суппортом мы тоже два берём, два по два модуля, как и коробок.
> Коробочки он правильно посчитал, а с суппортом он один посчитал»

**Подтверждено в коде** — [`js/posts.js:118`](../js/posts.js):
```js
return mechSum + price(comp.frame) + price(comp.support) + price(boxUnit) * comp.boxCount;
```
Коробка умножается на `comp.boxCount`, суппорт — нет. Для немецкой/французской накладки
на 2 поста (2+2): коробок 2, суппортов должно быть 2, в смету идёт 1.

**Фикс:** ввести `supportCount` (равен `boxCount` для модели `post`) в `postComposition()`,
использовать в `postCost()`, в смете и во всех документах.

### 3.2 🔴 Суппорт для центральных накладок не подбирается (блокер NEVE UP)

**Корень найден.** Конвертер читает из номенклатуры колонки `Принцип обработки` и
`Модульность для коробки` ([`tools/lib/nomenclature.mjs:210`](../tools/lib/nomenclature.mjs)),
но **не пробрасывает их в итоговый каталог**. Запись в каталоге:
```json
{"code":"09661.01","kind":"frame","slotCount":1, ...}
```
Есть только `slotCount: 1` (модули накладки). `findSupport()`
([`js/postfit.js:129`](../js/postfit.js)) берёт `target = frameModules` = 1, ищет суппорт
на 1 модуль, не находит → `null` → пустая строка в смете.

**Правильная логика:** для центральных накладок суппорт и коробка подбираются по
**модульности КОРОБКИ** (`boxModularity`), а не накладки.

Заказчик заложил в номенклатуру машиночитаемые коды алгоритма — колонка
**`Принцип обработки`**: `1M_CENTRAL` (102), `1M_CENTRAL_3` (24), `2M_CENTRAL` (137),
`BUTTON` (135), `2_OFFSET` (12), `NO_SUPPORT, AQUAPLATE` (12), `SCHUP` (6),
`NO_INNERS, AQUAPLATE` (4), `Bluetooth` (17).

**Фикс:** пробросить `principle` + `boxModularity` в каталог и переключить подбор
с эвристики на эти коды. Закрывает **все 296 «нестандартных» позиций разом**, а не только
NEVE UP.

**Важно — наша прежняя гипотеза была неверной:**

| Накладка | Предполагали | Факт из номенклатуры |
|---|---|---|
| `09661.*` (1М центр. в коробку 2М) | 09606 ❌ | **09602.1 или 09603.1** |
| `09672.*` (2М центр. в коробку 3М) | — | **09606** (вот чей это суппорт) |
| `09671.*` (1М центр. в коробку 3М) | 09613? | **артикул не назван** ⚠️ |

Существующая функция `supportTypeForBox()` уже выбирает 602/603 по коробке — ремарка
заказчика ложится на неё без переделки, надо лишь подать правильную модульность.

### 3.3 🟡 Двойной клик по посту на плане сбрасывает редактирование

## 4. Новые требования из записей

### 4.1 Порядок работы: начинать с монтажного стандарта

Сейчас конструктор начинается с рамки. Заказчик хочет как на **colors.vimar.com**:
1. **Монтажный стандарт** (итальянский = прямоугольные / немецкий = квадратные коробки)
2. Коллекция → материал → цвет рамки → цвет клавиш
3. Конфигуратор **сразу отсеивает неподходящее**

> «По-хорошему это первое, что должны мы выбрать. И по логике конфигуратор нам должен
> сразу отсеять все вот эти вот неподходящие для нас рамки»

### 4.2 Фиксация коллекции и цвета за помещением

**Это и есть ответ, зачем нужны комнаты.**
> «было бы лучше, если бы для каждого помещения фиксировался конкретный цвет,
> и он бы предлагал только подходящего цвета накладки»

### 4.3 Крупное окно выбора товаров

Вместо мелкого выпадающего списка — большое окно/панель с крупными картинками,
разделами по функциональным группам (изначально свёрнутыми), возможностью перетаскивания.
Функциональные группы уже есть в номенклатуре (колонка `Функциональная группа`):
выключатели и кнопки, силовые розетки, слаботочные интерфейсы, монтажные аксессуары.

### 4.4 Фильтры и поиск

- Фильтрация **по цвету** (сейчас белые и чёрные вперемешку).
- **Поиск по артикулу** — «поиск должен быть по всему, что угодно в списке фильтров».

### 4.5 Аксессуары к механизмам

> «добавление аксессуаров к механизму, типа термодатчик к терморегулятору
> или подсветка к выключателям»

- **Термодатчик в пол** к терморегулятору — опция (без него регулирует по воздуху).
- **Подсветка клавиш** — сейчас отображается как отдельный модуль, а должна вставляться
  в клавишу. Опция «считать подсветку или нет» + выбор цвета, **применяемая ко всем
  выключателям сразу**. В номенклатуре уже есть колонки
  `Спрашивать подсветку`, `Цвет подсветки`, `Позиция подсветки`.
- **Нужен от заказчика список**: к каким механизмам какие аксессуары применимы.

### 4.6 Настройка отображаемых столбцов в документах

Ключевое требование по документам. Заказчик хочет **галочками** выбирать столбцы:
`№` · `Наполнение` · `Модульность` · `Монтажная коробка` · `Артикул` · `Иллюстрация`

> «мне нужно, чтобы я просто дал задание работяге, какую монтажную коробку куда смонтировать.
> Информация о суппортах, о накладках — ему не нужна»
> «Артикулы, например, мне не нужно отправлять, я просто хочу картинку и визуализацию,
> чтобы никто не видел артикулы»

### 4.7 Сводная спецификация для поставщика

Отдельный документ: все одинаковые позиции сгруппированы с количествами
(«коробки монтажные такие-то — столько-то штук») — то, что отправляется поставщику.

### 4.8 Убрать одиночные элементы с плана

> «эту часть — одиночные элементы — можно сразу убрать, потому что элементы только
> в блоках будут. Отдельно кнопку нет смысла размещать»

Всё размещается **только постами**.

### 4.9 Взрыв-схема — выбор вида

Заказчик хочет выбирать: **общая сборка** или **взрыв-схема**. Подтвердил, что взрыв-схема
для монтажника — то, что нужно («я как монтажник — опа, я вижу… набрал, разложил»).
