## 1. Что это за проект

**ElectroPlan Pro** — веб-планировщик электрики (проектирование ЭУИ — электроустановочных
изделий: розеток, выключателей, постов). Пользователь загружает план помещения, расставляет
на нём электрику, привязывает элементы к комнатам, собирает электрические посты из модульных
рамок и механизмов и на выходе получает смету и коммерческое предложение (PDF).

- **Заказчик** — компания **ЦентрСвет** (отдельный клиент; лежит внутри `РАБОТА ЛЮКСАР/myProgects`,
  но к ЛЮКСАР отношения не имеет).
- **Поставщик оборудования для каталога** — **VIMAR** (не заказчик). Каталог наполняется из
  прайса `Прайс VIMAR Евро 01.07.26 (2) (2).xls` (валюта EUR, дата 01.07.2026).
- **Расположение кода:** `electro/electroplan-project/`.
- **Git:** реальный репозиторий — `electroplan-project/.git` (один коммит `first commit`, дальше —
  много незакоммиченного). `.git` в корне `electro/` — пустой/нефункциональный, **не трогать**.

## 2. Для чего он нужен

Инструмент проектировщика: ускорить путь «план помещения → расстановка электрики → смета/КП».
Целевой сценарий и однопользовательский/многопользовательский режим ещё окончательно не
зафиксированы заказчиком (см. `PLAN.md`, раздел 0). В перспективе — интеграция в **1С-Битрикс**.

## 3. Что используется / технологии

**Текущий прототип — полностью клиентский, на ванильном JS, без сборки.** Запускается статикой.

| Слой | Технология |
|------|-----------|
| Фронтенд | Ванильный JavaScript (ES-модули не используются, скрипты через `<script>`), HTML, CSS |
| Разметка приложения | `index.html` + `css/styles.css` |
| Логика редактора | `js/app.js` (~63 КБ — монолит: план, стены, комнаты, посты, смета, PDF) |
| Слой данных | `js/data.js` → `window.DataService` (режимы `mock` / `api`); каталог — `js/catalog-vimar.js` |
| Хранение (прототип) | LocalStorage (шаблоны постов, проекты); изображения — data-URL |
| Импорт планов | `js/planImport.js` — PNG/SVG напрямую; PDF через **PDF.js**; DXF — свой парсер (`vendor/dxf-parser`); DWG→DXF через **wasm-конвертер** (`vendor/dwgdxf`) |
| Классическая сегментация комнат | `js/roomSegmentation.js` на **OpenCV.js** (`vendor/opencv.js`, ~10 МБ): Otsu → сеть стен → distance transform + watershed → слияние → ортогонализация контуров |
| ML-распознавание | `js/floorplanML.js` — **YOLOv8** через **onnxruntime-web** (WebGPU→WASM fallback, `vendor/ort/`); модель `vendor/models/floorplan-yolo.onnx` (103 МБ FP32, 9 классов) |
| PDF (КП) | Печатная страница браузера + системный диалог «Сохранить как PDF» |
| Локальный запуск | `python -m http.server --directory electroplan-project 8420` (см. `.claude/launch.json`, конфиг `electroplan`) |

**Целевой бэкенд — 1С-Битрикс** (архитектура выбрана, скелет создан, но не подключён):
- Модуль `centrsvet.electroplan`, PHP-namespace `Centrsvet\Electroplan`, компонент `centrsvet:electroplan.app`.
- Скелет в `local/` (modules + components): репозитории товаров/постов/проектов, AJAX-контроллеры.
- Каталог — из инфоблока «Торговый каталог»; посты/проекты — Highload-блоки; авторизация — штатная.
- Принцип: фронт ходит за данными **только через `window.DataService`**; под Битрикс он реализуется
  адаптером поверх `BX.ajax.runAction`, а `app.js` не меняется.
- Для сервера подготовлены (как ориентир): `database/schema.sql` (PostgreSQL), `api/README.md`.

## 5. Что уже сделано

**Редактор и проектирование:**
- Загрузка плана, ручная обрисовка стен, подписи комнат, компактные пиктограммы объектов,
  карточка при наведении, перемещение объектов.
- Конструктор электрических постов: рамка из реального каталога, модульное заполнение проёмов
  с учётом `moduleSpan`, индикатор занятых/свободных модулей, обязательный подрозетник, фильтрация
  списка по остатку места, сохранение шаблона поста и размещение на плане.
- Автопривязка оборудования к комнате (point-in-polygon, grid — фолбэк).
- Смета (оборудование / материалы / работы) и печатная форма КП с сохранением в PDF.

**Импорт планов (`planImport.js`) — законченный клиентский сценарий:**
- PNG/SVG напрямую; PDF через PDF.js (выбор страницы в многостраничном, растеризация, лимит пикселей);
  ASCII DXF (model space: линии/полилинии/дуги/сплайны/блоки); DWG→DXF (R13–R2018) через wasm.
- Ограничения: файл ≤100 МБ, лимит сложности, понятные ошибки для бинарного DXF/повреждённых файлов.

**Каталог VIMAR (`catalog-vimar.js`, ~443 КБ):**
- Разобран прайс (7 376 строк), подготовлена импортная книга и SQL-схема.
- Рабочий каталог для приложения: 399 товаров (340 механизмов, 58 рамок, 1 подрозетник) с реальными
  артикулами, ценами EUR, изображениями, сериями совместимости (Idea, Neve Up, часть KNX).
- Для всех 340 механизмов проставлен реальный `moduleSpan` (по официальным каталогам Vimar).

**Автораспознавание комнат:**
- *Классический CV (`roomSegmentation.js`)* — работает на чётких планах; кнопка «Определить комнаты».
  Ортогонализация контуров, привязка к линиям стен, ROI по контуру здания (отсечение рамки/штампа).
- *ML-детекция (`floorplanML.js`)* — **фича «Распознать элементы (ML)» готова и проверена**: YOLOv8
  в браузере выводит цветные боксы стен/дверей/окон/колонн/лестниц + легенду со счётчиками.
  Валидировано на образце `639`: ~25 элементов точно по месту.

**Битрикс:** создан скелет модуля/компонента/репозиториев/контроллеров в `local/`.
`ProductRepository.php` расширен полями изображений, совместимости и `mountRect` (под текущий фронт).

## 6. Что предстоит сделать (по планам проекта)

Приоритеты из `PLAN.md` / `PLAN-segmentation.md` (статус на 2026-07-24):

**Приоритет 1 — довести автораспознавание комнат (главная незакрытая задача):**
- **Сборка комнат из ML-детекций не работает:** YOLO даёт стены отдельными боксами с зазорами на
  углах → барьер не замыкается → всё сливается в одну область (на `639` 644k из 778k px). Два пути,
  **ждём выбор заказчика/пользователя A/B** (`PLAN-segmentation.md`, Шаг 2):
  - **(A)** wall-line extension: мёрж/продление боксов стен в замкнутый граф → полигонизация;
  - **(B)** пивот на сегментацию (**CubiCasa5k**): сплошные маски стен/комнат без зазоров.
- Ручное редактирование вершин найденных полигонов (`PLAN-segmentation.md` 3.5), соединение
  разрывов, удаление ложных границ, хранение правок отдельно от изображения.
- Масштаб плана в реальных единицах и авторасчёт площади в м² (`PLAN.md` 3.3/3.4, Фаза 4).
- (Опц.) квантование ML-модели INT8 (~26 МБ) вместо 103 МБ FP32.

**Приоритет 2 — перенос на сервер / Битрикс (`PLAN.md` раздел 6):**
- Импорт прайса в живой каталог Битрикс; Highload-блоки для постов/проектов; изображения — в
  файловое хранилище; перевод `DataService` из `mock` в `api`; авторизация и права.
- Серверная генерация PDF с фиксацией номера КП, возможная привязка к CRM.
- Утвердить правила классификации 5 903 «непроверенных» строк прайса.

**Приоритет 3 — рефакторинг и надёжность (`PLAN.md` разделы 2, 5, 7):**
- Разбить монолитный `app.js` на модули; вынести магические числа в конфиг; единая функция расчёта
  сметы; решить про сборку (Vite) и типизацию.
- Настройки процентов работ/материалов в UI, реквизиты/логотип/номер в КП, скидки/НДС/количество,
  экспорт сметы в Excel/CSV, кабели и метраж трасс.
- Автотесты (смета, геометрия), обработка ошибок, автосохранение, адаптив, инструкция пользователя.

**Не закрытые вопросы раздела 0 `PLAN.md`** (нужны ответы заказчика): целевой сценарий (0.2),
источник каталога из Битрикс (0.4/0.5), этап интеграции (0.7), фиксировать проценты работ/материалов
или делать настройкой (0.9).
